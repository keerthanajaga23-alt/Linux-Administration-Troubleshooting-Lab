# Lab 10: Linux Log Analysis and Troubleshooting

## 1. Objective

The objective of this lab is to practise inspecting Linux system and service logs, filtering error messages, identifying events by time, and using log evidence to investigate service failures.

## 2. Lab Environment

* **Operating system:** Ubuntu 24.04 LTS
* **Platform:** Windows Subsystem for Linux 2 (WSL2)
* **Tools:** `journalctl`, `grep`, `tail`, `less`, `systemctl`
* **Services investigated:** Nginx, SSH, and BIND9, where available

Run the commands in your own Ubuntu environment. Record the actual results and mark tasks complete only after you have verified them.

## 3. What Are Linux Logs?

Logs are records of events generated by the operating system, services, and applications.

They can help an administrator determine:

* What happened.
* When it happened.
* Which service or process was involved.
* Whether an error or warning was recorded.
* What to investigate next.

Logs are an important part of troubleshooting, but a log message is evidence rather than automatic proof of the root cause.

## 4. Important Terms

* **Log:** A record of an event or activity.
* **System journal:** A collection of log records managed by `systemd-journald`.
* **Service log:** Messages associated with a particular service.
* **Error:** A recorded condition that indicates an operation failed.
* **Warning:** A condition that may require attention but does not necessarily mean the service has failed.
* **Timestamp:** The date and time associated with an event.
* **Root cause:** The underlying reason for a problem.
* **Log filtering:** Selecting messages based on criteria such as service, priority, or text.

## 5. View Recent System Logs

Run:

```bash
sudo journalctl -n 50 --no-pager
```

This displays the last 50 journal entries.

Command explanation:

* `journalctl` reads the system journal.
* `-n 50` requests the most recent 50 entries.
* `--no-pager` prints the output directly instead of opening a pager.

To view the journal in a scrollable interface, run:

```bash
sudo journalctl
```

If the output opens in `less`, press `q` to exit.

## 6. View Error-Level Messages

Run:

```bash
sudo journalctl -p err -n 30 --no-pager
```

This displays up to 30 recent journal entries at error priority.

The `-p err` option filters for error-priority messages.

A useful troubleshooting habit is to review the timestamp, service or process, and complete message before deciding what to do next.

**Important:** An old error may no longer describe the current problem. Always consider when the message occurred.

## 7. Inspect Logs for a Specific Service

### Nginx

```bash
sudo journalctl -u nginx -n 50 --no-pager
```

### SSH

```bash
sudo journalctl -u ssh -n 50 --no-pager
```

### BIND9

```bash
sudo journalctl -u named -n 50 --no-pager
```

The `-u` option filters journal entries by service unit.

If the service is not installed or has not generated journal entries, the result may be empty or indicate that the unit cannot be found. Verify the service name and installation status rather than assuming the absence of output means success.

## 8. Filter Logs by Text

To search Nginx journal messages for the word `error`:

```bash
sudo journalctl -u nginx --no-pager | grep -i error
```

To search BIND9 messages for several possible failure terms:

```bash
sudo journalctl -u named --no-pager | grep -iE 'error|failed|fatal'
```

Command explanation:

* `grep` searches text for matching patterns.
* `-i` makes the search case-insensitive.
* `-E` enables extended regular expressions.
* `|` passes the output of one command into another command.
* `error|failed|fatal` matches any of the listed terms.

A filtered search may omit important context. If a message looks relevant, inspect the surrounding journal entries as well.

## 9. Investigate Logs for a Time Period

To view messages from the current boot:

```bash
sudo journalctl -b --no-pager
```

To view messages from the current boot at error priority:

```bash
sudo journalctl -b -p err --no-pager
```

To inspect messages since a specified time, use:

```bash
sudo journalctl --since "1 hour ago" --no-pager
```

You can specify a date and time range as well:

```bash
sudo journalctl --since "2026-10-13 08:00:00" --until "2026-10-13 09:00:00" --no-pager
```

Use a time range that matches the actual incident. Ensure the time zone is understood when comparing application logs, system logs, and user reports.

## 10. Inspect Traditional Log Files

Some applications write to files under `/var/log/`.

List the directory:

```bash
ls -lah /var/log/
```

Common examples include:

```text
/var/log/nginx/access.log
/var/log/nginx/error.log
```

These Nginx files may be present if Nginx is installed and configured to use them.

View recent Nginx error-log entries:

```bash
sudo tail -n 50 /var/log/nginx/error.log
```

View the access log:

```bash
sudo tail -n 50 /var/log/nginx/access.log
```

Follow new entries as they are written:

```bash
sudo tail -f /var/log/nginx/error.log
```

Press `Ctrl + C` to stop following the log.

The access log records requests handled by the web server. The error log records operational messages and other diagnostic details. Exact contents depend on the configuration and events that occurred.

## 11. Search Traditional Log Files

Search the Nginx error log for error messages:

```bash
sudo grep -i error /var/log/nginx/error.log
```

Display matching lines with line numbers:

```bash
sudo grep -in error /var/log/nginx/error.log
```

The `-n` option displays the line number of each match.

If the file does not exist, check whether Nginx is installed and whether its logging configuration directs messages to a different location.

## 12. Troubleshooting Scenario: Nginx Website Is Unavailable

### Scenario

A user reports that a website on the Linux server is not opening.

### Step 1: Check the service

```bash
sudo systemctl status nginx --no-pager
```

### Step 2: Review recent service logs

```bash
sudo journalctl -u nginx -n 50 --no-pager
```

### Step 3: Inspect the Nginx error log, if present

```bash
sudo tail -n 50 /var/log/nginx/error.log
```

### Step 4: Validate the configuration

```bash
sudo nginx -t
```

### Step 5: Check the listening port

```bash
sudo ss -lntp | grep ':80'
```

### Step 6: Test the local HTTP response

```bash
curl -I http://localhost
```

### Troubleshooting workflow

1. Confirm the user's reported symptom and when it began.
2. Check the Nginx service state.
3. Review messages around the incident time.
4. Identify relevant errors and warnings.
5. Check configuration, listening ports, and dependencies as indicated by the evidence.
6. Correct the identified cause.
7. Validate and reload or restart the service when appropriate.
8. Repeat the HTTP test and record the outcome.

Do not assume that the latest error message is necessarily related to the website outage. Correlate it with the incident time and the other test results.

## 13. Troubleshooting Scenario: SSH Connection Failure

### Scenario

A user cannot establish an SSH connection to a Linux server.

On a server you administer, check recent SSH logs:

```bash
sudo journalctl -u ssh -n 50 --no-pager
```

Check service status:

```bash
sudo systemctl status ssh --no-pager
```

Check the listener:

```bash
sudo ss -lntp | grep ':22'
```

Validate SSH configuration syntax:

```bash
sudo sshd -t
```

Investigate messages related to the reported connection time. The logs and supporting tests may point to a service problem, authentication issue, configuration problem, or another cause.

Not every failed client connection is logged by the SSH service, and log detail varies with the server configuration.

## 14. Troubleshooting Scenario: BIND9 DNS Issue

### Scenario

A DNS query fails or the DNS service reports a warning.

Inspect recent BIND9 logs:

```bash
sudo journalctl -u named -n 50 --no-pager
```

Filter for error-related messages:

```bash
sudo journalctl -u named --no-pager | grep -iE 'error|failed|fatal'
```

Check whether BIND is active:

```bash
sudo systemctl is-active named
```

Validate the configuration:

```bash
sudo named-checkconf
```

Validate the local zone:

```bash
sudo named-checkzone lab.test /etc/bind/db.lab.test
```

Test the DNS record against the server address currently used by your lab:

```bash
dig @<DNS-IP> server.lab.test A
```

Replace `<DNS-IP>` with the actual address where BIND is listening.

During an earlier lab session, BIND returned the expected `192.168.1.20` address for `server.lab.test` when queried at `172.16.36.24`. The RNDC reload problem on port 953 remained unresolved.

When investigating the issue again, correlate the log timestamp with the reload attempt, check the actual error, validate the configuration, and test whether the server answers DNS queries. Do not treat every interface warning as proof that the zone itself is invalid.

## 15. A Structured Log-Analysis Method

Use this method when investigating a technical problem:

1. **Identify the symptom.** Find out what the user observed and when it happened.
2. **Select the relevant service.** For example, inspect Nginx logs for a web-server problem.
3. **Narrow the time range.** Focus on messages around the incident.
4. **Identify relevant messages.** Note warnings, errors, and related events.
5. **Check other evidence.** Compare logs with service status, configuration validation, network checks, and port information.
6. **Determine the likely cause.** Base the conclusion on supporting evidence.
7. **Apply a suitable correction.** Avoid unrelated changes.
8. **Verify recovery.** Repeat the original test.
9. **Document the result.** Record the symptom, evidence, cause, correction, and verification outcome.
